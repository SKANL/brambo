# ADR-006: Vendor CLIs as trait records; API executors through an explicit registry

## Status

Accepted. In force for 0.5.x.

## Context

brambo drives both coding CLIs (Claude Code, Codex, OpenCode) and hosted model APIs (OpenAI, Anthropic). Vendors are not interchangeable, and loading code named by configuration would let a configuration file choose what runs.

## Decision

- `adapter-cli` is one generic engine. Each CLI executor is a data record (command, fixed args, prompt delivery, output parsing), not a class: `claude-code`, `codex` and `opencode`.
- API executors live in `adapter-api` (registry, retry and tool-loop primitives) plus provider packages. A provider id selects a provider the host already registered; it never names a module to import.
- The host owns credentials, model choice, workspace, budgets and cancellation. There is no hidden vendor abstraction: each adapter maps its own vendor protocol.

## Consequences

- Adding a CLI executor is adding a trait record.
- Typed model controls require a declared executor version and a direct executable; a Windows `.cmd`/`.bat` shim is refused.
- `claude-code` runs with `--dangerously-skip-permissions` because there is no interactive approver in a headless run (see ADR-007).
- Both API providers call the retry machinery with `maxAttempts: 1`, so nothing is retried by default.

## Evidence

- `packages/adapter-cli/src/catalogue.ts` and `packages/adapter-cli/src/executors/*.ts`.
- `packages/adapter-api/src/registry.ts` and `packages/adapter-api/src/transport.ts`.
- `packages/adapter-openai/src/openai-provider.ts` and `packages/adapter-anthropic/src/anthropic-provider.ts` (`maxAttempts: 1`).
