# ADR-002: Puertos en contracts y una topología descendente impuesta

## Estado

Aceptada. Vigente en 0.5.x. En los comentarios del código se cita como AD-2.

## Contexto

Con 28 paquetes, un diagrama de dependencias en un documento no puede hacer fallar una compilación. Las protecciones anteriores se eludieron en la práctica: una vez con una importación relativa que entraba en otro paquete y otra con una reexportación que introducía composición en la CLI.

## Decisión

- Cada puerto, validador, error con código y suite de contrato vive en `@brambodev/contracts`.
- Cada paquete tiene un nivel numerado (de 0 a 8) y solo puede importar niveles estrictamente inferiores. La tabla de niveles es ejecutable y se comprueba en ambas direcciones: un paquete sin nivel falla, y un nivel para un paquete eliminado falla.
- Las importaciones relativas que salen de un paquete están prohibidas en todo el repositorio.
- `@brambodev/cli` es un binding delgado: no puede importar `node:fs` ni ningún nombre de composición de ningún paquete `@brambodev/*`.

## Consecuencias

- Añadir un paquete implica elegir su nivel en el mismo cambio.
- Los paquetes del mismo nivel no pueden importarse entre sí; por eso `lock` obtuvo su propio nivel cuando dos paquetes del nivel 2 lo necesitaron.
- Un autor de puertos puede depender solo de `@brambodev/contracts` y ejecutar las suites publicadas.
- La CLI no puede ser dueña de la composición, ni siquiera mediante una reexportación.

## Evidencia

- `packages/contracts/test/topology.test.ts` (el mapa `TIER` y la regla estrictamente descendente).
- `eslint.config.js` (`no-restricted-imports` para `../..`, la prohibición de `node:fs` en la CLI y la de nombres de composición, con comentarios que registran las elusiones que las motivaron).
- `packages/contracts/README.md` (instalación solo de contracts).
